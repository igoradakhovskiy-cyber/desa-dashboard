# Как развернуть этот формат отчёта на другой проект

Дашборд собран как переиспользуемый шаблон: пайплайн данных (`scripts/`) отделён от
представления (`src/`), а всё, что меняется от кабинета к кабинету, вынесено в переменные
окружения. Перенос на новый проект — это примерно час, из которых большая часть уходит
на два решения, описанных в разделе «Что решать под каждый кабинет».

Родословная: Lagoon Resort (`~/lagoon-dashboard`, 24.07.2026) → Desa Harmonis 2
(`~/desa-dashboard`, 25.07.2026, добавлен CRM-слой). Переносить надо с Desa — Lagoon
остался без CRM и с двумя языками.

---

## Шаг 1. Скелет

```bash
rsync -a --exclude node_modules --exclude .git --exclude dist \
      --exclude .data --exclude 'public/creatives/*' --exclude 'public/data/*' \
      ~/desa-dashboard/ ~/НОВЫЙ-dashboard/
```

Дальше — три места, где имя репозитория зашито:

| Файл | Что менять |
|---|---|
| `vite.config.ts` | `base: '/НОВЫЙ-dashboard/'` — **обязано совпадать с именем репо**, иначе все ассеты 404 |
| `package.json` | `name` |
| `index.html` | `<title>` |
| `src/App.tsx` | `PROJECT` (заголовок на экране входа) и `PW_KEY` (свой ключ сессии, иначе пароли дашбордов конфликтуют в одном браузере) |

## Шаг 2. Конфиг пайплайна

Всё через переменные окружения — правится в `env:` блоке `.github/workflows/deploy.yml`
и в дефолтах в шапке `scripts/fetch-meta.mjs`:

```
META_ACCOUNT_ID   act_XXXXXXXXXX
PROJECT_NAME      Название проекта
MIN_DATE          YYYY-MM-DD    старт нужного флайта, чтобы старые кампании не шумели
LEAD_TYPE         lead          см. «Что решать» ниже
PREVIEW_FORMAT    INSTAGRAM_STORY   для 9:16; для ленты — MOBILE_FEED_STANDARD
PLAN_BUDGET / PLAN_LEADS / PLAN_CPL / PLAN_QUAL / PLAN_CPQL
SHEET_ID / SHEET_TAB
```

**Прокидывать в CI надо все до единой.** В Lagoon workflow передавал только
`META_ACCOUNT_ID`, а остальное молча бралось из хардкода в скрипте — так дашборд
однажды и начнёт тихо показывать не то.

## Шаг 3. Деплой

```bash
cd ~/НОВЫЙ-dashboard && git init && git add -A && git commit -m "..."
gh repo create НОВЫЙ-dashboard --public --source=. --remote=origin
git push -u origin main

gh secret   set META_ACCESS_TOKEN   --repo ПОЛЬЗОВАТЕЛЬ/НОВЫЙ-dashboard   # системный токен Meta
gh secret   set DASHBOARD_PASSWORD  --repo ПОЛЬЗОВАТЕЛЬ/НОВЫЙ-dashboard
gh variable set META_ACCOUNT_ID     --body 'act_XXX' --repo ...
gh variable set SHEET_ID            --body '...'     --repo ...

# Pages включать этой командой, а НЕ через configure-pages в workflow:
gh api -X POST repos/ПОЛЬЗОВАТЕЛЬ/НОВЫЙ-dashboard/pages -f build_type=workflow
```

`actions/configure-pages@v5` с `enablement: true` падает на новом репо с
`Resource not accessible by integration` — у токена Actions нет прав создать Pages-сайт.
Один вызов `gh api` выше решает это навсегда, дальше workflow работает сам.

## Что решать под каждый кабинет

Три вещи нельзя скопировать — их надо проверить на живых данных.

### 1. Какое событие считать лидом

```bash
curl -s "https://graph.facebook.com/v21.0/act_XXX/insights?level=account\
&fields=spend,actions&date_preset=last_90d&access_token=$TOKEN"
```

Посмотреть `lead`, `offsite_conversion.fb_pixel_lead`, `onsite_web_lead`. На W_RES и
Homex все три совпадают, поэтому `lead` безопасен — но это свойство кабинета, а не
константа. Сверить с Ads Manager до того, как цифры уедут клиенту.

### 2. Откуда брать постеры креативов

Порядок источников уже зашит в `resolveCreative()`, но полезно знать, что произойдёт:

1. `object_story_spec.video_data.image_url` — **основной**. Полный размер 1080×1920,
   читается обычными рекламными правами. Работает везде.
2. Нода видео — даёт ещё и пермалинк, но требует прав на Страницу.
3. `creative.thumbnail_url` — последний резерв, всего 64×64 (параметр `stp` подписан,
   размер подменить нельзя).

Если у приложения нет прав на Страницу кабинета (как на W_RES), пункт 2 отдаёт ошибку
`#10` — это нормально и обработано. Пермалинков «Открыть в Instagram» тогда не будет.

### 3. Языковые потоки

`langToken()` в `scripts/fetch-meta.mjs` разбирает имя вида
`403_EN_WW_DESA2_AQ_[CPL]_ABO_27.06.2026` — язык вторым токеном. Если в новом кабинете
нет языкового деления, проще убрать `LangSplit` и переключатель в шапке, чем городить
искусственные потоки. Список языков — `LANGS` в `src/types.ts`, цвета — `langColor()`.

## CRM-слой

### Предусловие, без которого ничего не поедет

У объявлений в кабинете **должны** стоять UTM-макросы:

```
utm_source=facebook&utm_campaign={{campaign.name}}&utm_content={{ad.name}}
```

Тогда в выгрузке CRM `UTM Campaign` — это имя кампании, а `UTM Content` — имя объявления,
и они сходятся с API точным совпадением (регистр игнорируется). **Проверить это до
начала работы** — если макросов нет, джойна не будет вообще, и CRM-слой надо выключать.

### Два листа, два слоя

Пайплайн читает **две вкладки**, и это два независимых слоя с независимым здоровьем:

| вкладка | env | что даёт | если сломается |
|---|---|---|---|
| `client_data` | `SHEET_TAB` | все лиды: количество, «текущий статус», лиды по странам | замирают лиды CRM и % квалификации |
| `История статусов` | `HIST_TAB` + `HIST_GID` | только квалы, по колонке на этап: квалы, воронка глубже квала, квалы по странам | замирают квалы, CPQL и воронка |

Второй слой опционален по смыслу: если на новом проекте нет листа с историей статусов,
воронка глубже квала просто не появится, но квалы придётся вернуть на `client_data` —
сейчас они читаются **только** из `История статусов`.

### Настройка под другую таблицу

- `client_data` — править `COL` и `EXPECTED_HEADER` в `scripts/fetch-crm.mjs`: там индексы
  колонок и эталонная шапка. По индексу, потому что в шапке дубли имён (см. грабли).
- `История статусов` — править `HIST_FIELDS` (имена колонок) и `STAGES_REQUIRED`. Колонки
  ищутся **по имени заголовка**, а этапы вообще не перечисляются: этап = любой заголовок
  вида `NN.Название` правее `UTM Content`. Порядок этапов — порядок колонок в листе.
- Русские подписи этапов — `STAGE_LABEL` / `STAGE_SHORT` в `src/config.ts`. Не источник
  правды: этап без подписи покажется под своим ключом, а не исчезнет.

Валидацию шапки **не отключать**, см. грабли ниже.

### Как таблица тянется онлайн

Если таблица открыта на чтение по ссылке — обычный `fetch` CSV-экспорта, ни OAuth, ни
сервисного аккаунта не нужно:

```
https://docs.google.com/spreadsheets/d/<ID>/gviz/tq?tqx=out:csv&sheet=<TAB>
```

Проверить доступность: `curl -s -o /dev/null -w "%{http_code}" "<url>"` → 200 значит
читается анонимно. Если 401/403 — таблица закрыта, нужен сервисный аккаунт + Sheets API
с JSON-ключом в GitHub Secrets (~40 строк, отдельный заход).

Обновление раз в 3 часа: оба сборщика в одном прогоне GitHub Actions, поэтому реклама и
CRM всегда из одного среза. Браузер клиента в Google не ходит — страница показывает срез
на момент сборки.

## Грабли, каждая из которых уже стоила времени

**gviz не отдаёт 404 ни на неверное имя вкладки, ни на неверный `gid` — молча возвращает
первую.** Так «Client Data» тихо превратилось в вкладку `dashboard`. Отсюда жёсткая
валидация шапки с падением: без неё пайплайн зашифрует мусор и никто не заметит. Именно
поэтому фолбэк `gid` → имя вкладки безопасен: обе попытки проходят через проверку шапки.

**Дубли имён колонок.** В таблице Desa две колонки называются `Квалификация` — F
(`Qualified`) и Z (`1`, другая логика). Поэтому на `client_data` колонки читаются **по
индексу**, а не по имени. Проверять это на каждой новой выгрузке: если имена уникальны,
лучше по имени — вставленная колонка тогда ничего не ломает.

**Квал — это факт строки, а не значение ячейки.** На листе `История статусов` у ~7% строк
дата в `05.Qualified` не проставлена, хотя сделка ушла дальше по воронке. Считать квалы по
этой колонке — потерять их.

**Воронка в CRM не монотонна.** 52 сделки имеют дату `07.Online Meeting` без даты
`06.Meeting Set` — продажи проставляют следующий статус, пропустив предыдущий, и никогда не
возвращаются заполнить. Поэтому этап считается кумулятивно: дата **на нём или глубже**.
Подсчёт по своей колонке даёт воронку, которая растёт вниз, и её сразу перестают читать.

**Прочерк в UTM — это не имя кампании.** CRM пишет `—`, когда лид пришёл не из рекламы.
Без нормализации он идёт в лукап кампаний, не находится и попадает в `unknown_campaign` —
то есть органика отчитывается как «старый флайт», а join-rate, по которому ловится
реально сломанный джойн, уезжает вниз.

**Резолв креатива не должен ронять объявление.** В исходном коде Lagoon `ads.push()`
стоял после `await resolveCreative()`, и когда на W_RES посыпались ошибки #10, из выгрузки
пропали **все 28 объявлений** — при этом скрипт завершился успешно и написал «ads 0».
Сейчас резолв обёрнут в try/catch: метрики важнее картинки.

**Лиды со старых флайтов.** Строки CRM, чья кампания вне окна дашборда, в CPQL не
считаются — их расхода в окне тоже нет, иначе цена квала занижается. Они не выбрасываются
молча, а попадают в `unmatched` и видны в диагностической полосе.

**Ассерты не должны стоять в CI.** Таблица растёт каждый день, поэтому сверка с эталонным
срезом живёт под флагом `--verify` (`npm run crm:verify`) и запускается руками. В CI —
только структурные проверки, которые не дрейфуют: шапка, ноль строк, match-rate < 50%.

## Проверка после переноса

```bash
npm install
npm run crm:test    # офлайн, без сети: устойчивость к правкам в таблице
npm run data        # Meta → CRM → шифрование; нужен DASHBOARD_PASSWORD
npm run typecheck
npm run dev
```

Сверить печатаемый cross-check с Ads Manager: расход, лиды, match-rate обоих листов и
воронку по этапам. Затем — главная проверка, что защита на месте:

```bash
HIST_TAB=нет-такой-вкладки HIST_GID=999999 node scripts/fetch-crm.mjs   # должно упасть
SHEET_TAB=нет-такой-вкладки node scripts/fetch-crm.mjs                  # должно упасть
HIST_GID=999999 node scripts/fetch-crm.mjs   # должно восстановиться по имени вкладки
```

Если первые две команды отработали успешно — валидация шапки не на месте, и пайплайн
зашифрует содержимое случайной вкладки.

Глазами по интерфейсу: воронка убывает сверху вниз, у каждого этапа есть цена, переключатель
«по дате лида / по дате события» меняет цифры, пустые этапы не рисуются ни плитками, ни
колонками в таблице кампаний.
