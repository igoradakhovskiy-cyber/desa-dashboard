# Desa Harmonis 2 — живой рекламный дашборд

Интерактивный отчёт по рекламе Meta (Facebook / Instagram) для проекта Desa Harmonis 2.
Данные тянутся из рекламного кабинета **W_RES** (`act_1113679997274561`) через Meta Marketing API
**и** из выгрузки CRM в Google-таблице, джойнятся по UTM, обновляются каждые 3 часа и
публикуются на GitHub Pages за паролем.

## Что внутри
- KPI: расход, лиды, CPL, **квал-лиды, цена квал-лида (CPQL)**, % квалификации + план/факт месяца.
- Полоса качества данных: сколько лидов CRM удалось сопоставить с рекламой и почему остальные — нет.
- Динамика по дням, воронка (показы → клики → лиды → квалы), потоки **EN / DE / RU**.
- **Воронка продаж глубже квала** (квал → встреча → онлайн-встреча → … → оплата) с ценой каждого
  этапа и переключателем «по дате заявки / по дате этапа», и **география лидов** с процентом
  квалификации по странам.
- Кампании с дрилл-дауном: кампания → адсет → объявление, с квалами и CPQL.
- **Плейсменты** — расход, показы, CTR, лиды и CPL по каждому плейсменту, плюс
  переключатель на уровень площадок (Facebook / Instagram / Audience Network / Threads).
- **Галерея креативов** — постеры 9:16, сортировка по квалам / CPQL, живое превью Meta в модалке.

## Стек
Vite + React + TypeScript + Tailwind v4 + Recharts. Данные — один зашифрованный файл
`public/data/latest.enc` (AES-256-GCM, ключ из пароля через PBKDF2). Сборщики — Node 18+
без внешних зависимостей.

## Локально
```bash
npm install
npm run data       # Meta + CRM + шифрование одной командой
npm run dev        # http://localhost:5181/desa-dashboard/
```

`npm run data` = `fetch-meta.mjs` → `fetch-crm.mjs` → `encrypt-data.mjs`.
Для шифрования нужна переменная `DASHBOARD_PASSWORD`.
Токен Meta берётся из `~/.config/claude-meta/token.env` или из `META_ACCESS_TOKEN`.

## Как обновляются данные

Каждые 3 часа GitHub Actions запускает оба сборщика **в одном прогоне**, поэтому реклама
и CRM всегда из одного среза и не расходятся между собой.

**Meta** — `scripts/fetch-meta.mjs`, Graph API. Настройки: `META_ACCOUNT_ID`, `MIN_DATE`,
`LEAD_TYPE`, `PLAN_BUDGET`, `PLAN_LEADS`, `PLAN_CPL`, `PLAN_QUAL`, `PLAN_CPQL`, `PREVIEW_FORMAT`.

**CRM** — `scripts/fetch-crm.mjs` читает **две вкладки** Google-таблицы обычным `fetch`
CSV-экспорта. Таблица открыта на чтение по ссылке, поэтому **не нужны** ни OAuth,
ни сервисный аккаунт, ни API-ключ. Настройки: `SHEET_ID`, `SHEET_TAB`, `HIST_TAB`, `HIST_GID`.

| вкладка | что даёт |
|---|---|
| `client_data` | все лиды CRM: количество лидов, «текущий статус» сделки, лиды по странам |
| `История статусов` | только квал-лиды, по колонке на каждый этап воронки: квалы, вся воронка глубже квала, квалы по странам |

Это два независимых **слоя** с независимым здоровьем: сломался один — он замораживается
на последней достоверной версии, второй продолжает обновляться.

Страница показывает срез на момент последней сборки (максимум 3 часа), браузер клиента
в Google не ходит. Нужно прямо сейчас — кнопка **Run workflow** в Actions, ~2 минуты.

### Как устроен джойн

У всех объявлений в `url_tags` стоит
`utm_source=facebook&utm_campaign={{campaign.name}}&utm_content={{ad.name}}`,
поэтому колонка `UTM Campaign` — это имя кампании, а `UTM Content` — имя объявления,
и они сходятся с API по точному совпадению (регистр игнорируется).

На `client_data` колонки читаются **по индексу, а не по имени**: в шапке есть вторая
колонка с тем же именем `Квалификация` (Z) с другой логикой, и поиск по имени взял бы не ту.
На `История статусов` — наоборот, **по имени заголовка**: там все заголовки уникальны, а
вкладку ведут руками, и вставленная колонка не должна ничего сдвигать.

Строки, которые не удалось сопоставить, не выбрасываются молча — они попадают в блок
`unmatched` с причиной и видны в интерфейсе. Лиды со старых флайтов (вне окна дашборда)
в CPQL не считаются: их расхода в окне нет, иначе цена квала была бы занижена.
Прочерк `—` в UTM-колонках означает «лид не из рекламы» (WhatsApp, прямой заход) и
попадает в `no_utm`, а не в «неизвестная кампания».

### Воронка глубже квала

Квал-лид — это **факт наличия строки** на вкладке `История статусов`, а не значение ячейки:
на этом листе лежат только квалы, и примерно у 7% строк дата в `05.Qualified` не проставлена,
хотя сделка явно ушла дальше.

Этапы — колонки `05.Qualified` … `13.Contract Payment Received`. Этап засчитывается, если
дата стоит **на нём или на любом более глубоком**. Это не педантизм: продажи регулярно
проставляют следующий статус, пропустив предыдущий (по всему листу 52 сделки имеют дату
`07.Online Meeting` без даты `06.Meeting Set`), и подсчёт по своей колонке дал бы воронку,
которая растёт вниз.

Список этапов берётся **из самой шапки** — любой заголовок вида `NN.Название` правее
`UTM Content`. Добавили в таблицу новый этап — он приедет в дашборд сам, на следующем прогоне.

У каждого события две даты, между ними в интерфейсе переключатель:

| режим | смысл |
|---|---|
| по дате лида | событие относится ко дню создания лида — к тому расходу, который этот лид купил. Честная когорта, но последние дни всегда недосчитаны |
| по дате события | событие относится ко дню, когда этап реально произошёл — виден темп отдела продаж, но расход периода делится на события лидов из других периодов |

Цена этапа = расход за период / число дошедших до этапа.

### ⚠️ Фильтр на вкладке ломает выгрузку

**CSV-экспорт Google Sheets отдаёт только видимые строки.** Любой фильтр, оставленный
на вкладке, обрезает выгрузку до того, что через него прошло — шапка при этом на месте,
вкладка та же, и внешне всё выглядит целым.

Так и случилось 27.07.2026: фильтр забыли снять, таблица отдала 33 строки вместо 3118,
match-rate упал до 10%, `fetch-crm.mjs` вышел с кодом 1 — и увёл за собой весь job.
Деплой не доехал, Pages двое суток отдавал сборку от 27-го, хотя данные Meta были в порядке.

Лечится снятием фильтра: **Данные → Отключить фильтр**, дальше данные подтянутся сами.

### Проверки

Ошибка источника CRM **больше не роняет деплой**. Проблемы делятся на два класса:

| | что делает |
|---|---|
| структурное (не тот таб, нет обязательной колонки или этапа) | падает — данные читать нельзя в принципе |
| источник (обрезан, не сходится, поехал формат даты) | предупреждает, деплоит свежую Meta, замораживает **только сломанный лист** |

Во втором случае `fetch-crm.mjs` берёт **последний достоверный слой из уже задеплоенного
`latest.enc`** (расшифровывает его тем же `DASHBOARD_PASSWORD`), кладёт его обратно и
проставляет `crm.health_sources`. Заморозка **по-источниковая**: сломался `client_data` —
замирают лиды CRM и % квалификации, воронка по этапам живёт; сломалась `История статусов` —
замирают квалы, CPQL и воронка, а лиды остаются свежими. В интерфейсе появляется баннер с
названием листа, причиной и датой среза. Как только таблица чинится — следующий прогон сам
возвращается к живым данным.

Базовая линия берётся именно из задеплоенного артефакта: это не требует `contents: write`,
не плодит коммит каждые 3 часа и самовосстанавливается.

`diagnose()` различает **обрезанный источник** (строки пропали, оставшиеся сходятся) и
**сломанный джойн** (строки на месте, перестали сопоставляться) — у них разные причины
и разное лечение, а голый порог match-rate их путает.

Отдельная проверка на стороне Meta: расход по плейсментам сверяется с расходом аккаунта,
расхождение больше 1% валит сборку — значит breakdown-проход недобрал строк.

Проверка шапки остаётся жёсткой, потому что **gviz не отдаёт 404 ни на неверное имя вкладки,
ни на неверный `gid` — он молча возвращает первую**. Без неё пайплайн зашифровал бы мусор и
никто бы не заметил. `История статусов` тянется сначала по `gid` (переживает переименование
вкладки), при несовпадении шапки — по имени; проверка шапки идёт в обоих случаях.

### Что можно делать в таблице, не сломав дашборд

`npm run crm:test` — офлайн-прогон по фикстурам, без сети. Проверяет ровно то, что люди
делают с Google-таблицей руками:

| действие | результат |
|---|---|
| сортировка строк | ничего не меняется — всё агрегируется по ключам |
| вставили колонку в середину | цифры не двигаются: поиск по имени заголовка |
| добавили новый этап в конец воронки | приезжает в дашборд сам, под своим ключом, пока ему не задали русскую подпись в `STAGE_LABEL` |
| переименовали вкладку | подхватывается по `gid` |
| оставили фильтр | `source_truncated` → заморозка слоя + баннер с подсказкой снять фильтр |
| переформатировали колонку с датой | `date_format_broken` → заморозка, а не молчаливая потеря строк |
| написали текст вместо даты этапа | этап не засчитан, сделка учтена по последнему нормальному этапу, счётчик в диагностике |
| удалили обязательную колонку или этап | падение с явным сообщением, какой колонки нет |

```bash
npm run crm:test                # 26 проверок устойчивости, офлайн
npm run crm:verify              # сверка с эталонным срезом
node scripts/fetch-crm.mjs --strict   # локально: падать, а не деградировать
```

## Деплой (GitHub Pages + авто-крон)
1. Создать репозиторий **`desa-dashboard`** (имя важно — под него настроен `base` в `vite.config.ts`).
2. Settings → Pages → Source = **GitHub Actions**.
3. Settings → Secrets and variables → Actions:
   - Secret `META_ACCESS_TOKEN` — системный токен Meta.
   - Secret `DASHBOARD_PASSWORD` — пароль входа в дашборд.
   - Variable `META_ACCOUNT_ID` = `act_1113679997274561`.
   - Variable `SHEET_ID` = id Google-таблицы с выгрузкой CRM.
4. `git push` → workflow соберёт и опубликует сайт, дальше пересборка каждые 3 часа.

Итоговая ссылка: `https://<user>.github.io/desa-dashboard/`

## Безопасность
Расшифровка происходит в браузере: неверный пароль — данные просто не расшифруются,
обойти через DevTools нечего. В репозиторий не попадают ни токен, ни `.data/latest.json`,
ни постеры — всё пересобирается в CI при каждом прогоне.

Отдельно стоит держать в голове: сама Google-таблица сейчас **читается любым, у кого есть
ссылка**. Если закрыть доступ, сборка упадёт — тогда нужен сервисный аккаунт + Sheets API
с JSON-ключом в GitHub Secrets.

## Оговорка по квал-лидам и глубоким этапам
В режиме «по дате лида» событие привязано к дате создания лида, поэтому цифры за последние
дни ещё дорастут — свежий CPQL всегда выглядит хуже, чем окажется через неделю. С глубокими
этапами это выражено сильнее: до онлайн-встречи лид доходит не в день заявки, и «цена
онлайн-встречи» за последнюю неделю почти всегда завышена просто потому, что встречи ещё
не состоялись.

Режим «по дате события» этого не лечит, а меняет вопрос: он показывает, что произошло в
периоде, но делит расход периода на события лидов из других периодов. Для оценки эффективности
закупки правильный режим — «по дате лида»; для контроля работы отдела продаж — «по дате события».

## Оговорка по квалам в плейсментах
Расход, показы, клики, лиды и CPL по плейсментам — **фактические**, из Meta.

Колонки «квалы оц.» и «CPQL оц.» — **расчётные**. В выгрузке CRM нет поля плейсмента:
строка лида знает свою кампанию и объявление, но не знает, пришёл он из Reels или Stories.
Поэтому квалы каждого объявления разносятся по его собственным плейсментам пропорционально
лидам — объявление с 10 квалами, у которого 70% лидов пришло из Reels, отдаёт в Reels 7.

Считается **по каждому объявлению отдельно**, а не общим средним: плейсмент-микс у
объявлений расходится сильно, и усреднение по всему аккаунту обесценило бы цифру.
Квалы объявлений, не давших лидов в периоде, разнести нельзя — они показаны отдельной
строкой под таблицей, а не размазаны молча.

Чтобы мерить это фактически, нужно добавить `{{placement}}` в `utm_term` объявлений —
тогда плейсмент приедет в CRM вместе с лидом.
